# RANCAGE 0.2 Stage 0 — M0.3 Compiler & IR Architecture Specification

## 1. Overview & Scope

Milestone M0.3 bridges the typed Abstract Syntax Tree (AST) front-end developed in M0.1 and M0.2 with portable bytecode emission. It defines the RANCAGE-IR 0.2 schema, implements 10 Stage 0 bytecode opcodes, specifies intrinsic lowering to standard CALL operations with strict stack balance, and utilizes AST type metadata for ambiguous operator resolution.

### Scope:
- **RANCAGE-IR 0.2 Schema**: Container format version `0.2`, adding nominal `records` declarations alongside `functions`.
- **Typed AST Metadata**: Annotate `Expr.inferred_type` during static type checking to eliminate indexing opcode ambiguity.
- **10 Stage 0 Opcodes**: Emitting collections, field access/mutation, and composite element indexing.
- **Intrinsic Lowering**: Emitting `CALL <name> <arity>` for standard library intrinsics under uniform stack balance guarantees.
- **Collection Construction Order**: Left-to-right operand evaluation for lists, maps, and records.

---

## 2. RANCAGE-IR 0.2 Schema Specification

The IR 0.2 payload is a JSON-serializable dictionary preserving compatibility with VM container expectations while capturing record types.

```json
{
  "format": "RANCAGE-IR",
  "version": "0.2",
  "module": "main",
  "entry": "main",
  "records": {
    "Point": {
      "fields": [
        {"name": "x", "type": "int"},
        {"name": "y", "type": "int"}
      ]
    }
  },
  "functions": {
    "main": {
      "params": [],
      "return_type": "int",
      "code": [
        ["PUSH", 0],
        ["RETURN"]
      ]
    }
  }
}
```

## 3. Bytecode Instruction Set (Stage 0 Extensions)

M0.3 introduces 10 new opcodes, expanding the instruction set from 23 legacy opcodes to 33 total instructions.

| Opcode | Operands | Stack Inputs | Stack Outputs | Description |
|---|---|---|---|---|
| `MAKE_LIST` | `count: int` | `[e0, ..., en-1]` | `[list]` | Pops `count` elements, constructs homogeneous list. |
| `LIST_GET` | none | `[list, index]` | `[element]` | Pops `index` (int), pops `list`; pushes element at index. |
| `LIST_SET` | none | `[list, index, value]` | none | Pops `value`, pops `index`, pops `list`; mutates element in-place. |
| `MAKE_MAP` | `count: int` | `[k0, v0, ..., kn-1, vn-1]` | `[map]` | Pops `2*count` elements, constructs string-keyed map. |
| `MAP_GET` | none | `[map, key]` | `[value]` | Pops `key` (string), pops `map`; pushes value. Raises runtime error on missing key. |
| `MAP_SET` | none | `[map, key, value]` | none | Pops `value`, pops `key`, pops `map`; mutates or inserts key-value pair. |
| `MAKE_RECORD` | `name: str, fields: list[str]` | `[v0, ..., vn-1]` | `[record]` | Pops field values, constructs record instance of nominal type `name`. |
| `GET_FIELD` | `field: str` | `[record]` | `[value]` | Pops `record`, pushes value of named field. |
| `SET_FIELD` | `field: str` | `[record, value]` | none | Pops `value`, pops `record`; mutates field `field` in-place. |
| `STRING_GET` | none | `[string, index]` | `[char]` | Pops `index` (int), pops `string`; pushes 1-character string. |

## 4. AST Type Metadata & Indexing Opcode Dispatch

### Type Annotation (`inferred_type`)
`Expr` base class defines `inferred_type: str | None = None`. During `TypeChecker._expr()`, every evaluated expression node is annotated with its resolved static type string.

### Indexing Dispatch
The compiler resolves `IndexExpr` and `IndexAssign` via `target.inferred_type`:
- `list[T]` -> `LIST_GET` / `LIST_SET`
- `map[string, V]` -> `MAP_GET` / `MAP_SET`
- `string` -> `STRING_GET` (index assignment forbidden by type checker)

If `target.inferred_type` is absent, the compiler raises `RancageCompilerError`.

## 5. Intrinsics Lowering & CALL Stack Contract

Standard library intrinsics (`len`, `push`, `pop`, `ord`, `chr`, `slice`, `map_has`, `map_remove`) are lowered directly to `CALL <name> <arity>`.

### CALL Stack Balance Invariant:
1. Every call instruction (`CALL`) pushes exactly **1** operand onto the evaluation stack.
2. Value-returning functions and intrinsics (`len`, `pop`, `ord`, `chr`, `slice`, `map_has`, `map_remove`) push their return value.
3. Void functions and void intrinsics (`push`, `print`) push the `null` sentinel value (`None`).
4. Expression statements (`ExprStmt`) unconditionally emit `POP` after expression evaluation, discarding the returned value or `null` sentinel.
5. Net operand stack effect of any expression statement is **0**.

---

## 6. Collection Construction Evaluation Order

Operands during collection construction are strictly evaluated left-to-right:
1. `ListLiteral([e0, e1, ...])`: Evaluates `e0`, `e1`, ..., then emits `MAKE_LIST len`.
2. `MapLiteral([(k0, v0), ...])`: Evaluates `k0`, `v0`, `k1`, `v1`, ..., then emits `MAKE_MAP len`.
3. `RecordInit(name, [f0: v0, ...])`: Evaluates `v0`, `v1`, ..., then emits `MAKE_RECORD name [f0, f1, ...]`.

---

## 7. Runtime Boundaries (M0.3 vs M0.4)

Milestone M0.3 exclusively governs bytecode emission and IR verification:
- Compiler emits validated IR 0.2 containing 10 Stage 0 opcodes and record metadata.
- VM bytecode execution of Stage 0 opcodes is deferred to Milestone M0.4.
- Legacy VM 0.1 compatibility is preserved for existing 0.1 language programs.
